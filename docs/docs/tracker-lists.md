# Tracking the Trackers

On 2016 April 24, the GitHub user ngosang published a list of 49 open BitTorrent trackers. A small program has checked the list and republished it every day since, and ten years later, three of the 49 are still on it: `tracker.opentrackr.org`, `explodie.org`, and `open.stealth.si`. The others stopped answering, one by one, while every torrent made with their addresses went on naming them, because a torrent file or a magnet link carries the trackers written into it when it was made, and those never change.

So someone has to know which trackers still answer. This article follows that question: how a torrent names its trackers, and the conventions that grew up around naming them; the people who run open trackers, check them, and keep lists of the ones that work; the clients that read those lists; and what the checking leaves out. Then it introduces what ftorrent built for the same job, the public record at [list.ftorrent.com](https://list.ftorrent.com) and the Trackers tab in the desktop client. ftorrent also runs one of the trackers on these lists, `open.ftorrent.com`, and the last section follows it through every list as a worked example. Every count here was taken in 2026 November.

## What a tracker does

A tracker answers one question: who else has this torrent? A client joining a swarm sends the tracker an announce, carrying the torrent's info hash, the port the client listens on, and how much it has left to download. The tracker answers with other peers that announced the same hash, and with an interval to wait before announcing again. It holds no files and no torrents, only recent announces, in memory. An open tracker answers anyone, for any info hash, with no account.

Trackers speak three protocols:

- **HTTP**, from BitTorrent's original specification, [BEP 3](https://www.bittorrent.org/beps/bep_0003.html). An announce is a web request, and the answer is a bencoded dictionary. HTTPS is the same exchange over TLS.
- **UDP**, from [BEP 15](https://www.bittorrent.org/beps/bep_0015.html). The same exchange in a few small datagrams, after a short connect step that proves the client's address isn't forged. Many open trackers speak only UDP, since it costs the server far less per announce.
- **WebSocket**, defined by the [WebTorrent](https://webtorrent.io/) project for peers in a web page, which can reach other peers only through WebRTC. The page keeps a WebSocket open to the tracker, and the tracker both lists peers and relays the offers and answers that let two browsers connect directly.

Peers can also find each other without any tracker, through the distributed hash table and peer exchange, which [How the DHT Works](/how-the-dht-works) explains. A tracker is usually the fastest first introduction, though, and for a browser peer, which has no DHT, a WebSocket tracker is the only one.

## How a torrent names its trackers

BEP 3 gave a torrent file one tracker, in a key called `announce`. One tracker is one point of failure, and the fix came as the multitracker extension, which John Hoffman [published by 2003 July](https://web.archive.org/web/20030901063506/http://home.elp.rr.com/tur/multitracker-spec.txt) alongside the experimental client that became BitTornado, and which became [BEP 12](https://www.bittorrent.org/beps/bep_0012.html) in 2008 with its rules unchanged. It adds a key called `announce-list`, which holds tiers: a list of lists of trackers. BEP 12 gives the two shapes a purpose each. A tier with one tracker in it is a backup, tried only if the tiers before it fail, "meant for when the trackers are standard and can not share information." A tier with several trackers in it is "meant for trackers which can trade peer information": one operator's servers, sharing one swarm, which a client shuffles and tries in turn, so the load spreads across them and the swarm stays whole. Either way, the spec's client talks to one tracker at a time, the first that answers, and every client goes down the tiers in the same order, so a whole swarm meets at the same tracker and moves to the backup together.

A magnet link carries its trackers too. [BEP 9](https://www.bittorrent.org/beps/bep_0009.html) defines the link's form, where each `tr=` parameter names one tracker: "If there are multiple trackers, multiple tr entries may be included," and a link with none leaves the client to find peers through the DHT.

The trackers a person adds by hand travel as plain text, one address to a line, and the lists in this article are written that way, with a blank line between every two trackers. The blank line is a tier boundary, and the clients say so: qBittorrent's torrent creator tells its user "You can separate tracker tiers / groups with an empty line," and Transmission's tracker editor, "To add a new primary URL, add it after a blank line." So each tracker in such a list sits in a tier of its own. What a client does with that depends on one choice. qBittorrent turns on "announce to all tiers" by default, Transmission announces to the current tracker of every tier, and µTorrent's manual says it "announces to all tracker tiers simultaneously, but only one tracker per tier"; with one tracker to a tier, that's every tracker on the list. libtorrent, the library inside qBittorrent and Deluge, names both sides of the choice in its [settings](https://www.libtorrent.org/reference-Settings.html): announcing to one tracker in each tier "is the uTorrent behavior. To be compliant with the Multi-tracker specification, set it to false," and false is its default. Deluge keeps that default, so a torrent with twenty trackers, one to a tier, is announced to the first of them that answers from Deluge, and to all twenty from qBittorrent. This is how BitTorrent came to use the backup form of BEP 12 for something BEP 12 doesn't describe: a list of independent trackers, each holding part of the swarm, joined up by the DHT and peer exchange.

How many trackers a torrent should name has no answer in any spec, so here is what publishers ship. Ubuntu's release torrents name two, `torrent.ubuntu.com` and an IPv6-only twin, one to a tier. Debian's name one, beside two web seeds. The Internet Archive's name two of its own, beside three web seeds. The magnet link WebTorrent's documentation uses as its example names eight, five UDP trackers and three WebSocket ones. And ngosang's shortest list, `trackers_best.txt`, holds twenty. A torrent file can carry many trackers at no cost to anyone reading it, but a magnet link grows with each tracker, by fifty characters or so for an address of ordinary length once it's encoded: five trackers make a link of a little over 300 characters, and twenty make one over a thousand, long enough that some forums cut it off and a QR code gets hard to scan.

## The trackers

The open trackers that appear most often on the lists run on two programs. [opentracker](https://erdgeist.org/arts/software/opentracker/), written in C by erdgeist, is the older. [Aquatic](https://github.com/greatest-ape/aquatic), which Joakim Frostegård has written in Rust since 2020, speaks all three protocols in separate binaries; ftorrent's own tracker runs on it, and [Software Selections](/software-selections) weighs the two.

The best-known open trackers include `open.demonii.com`, which publishes figures in the tens of millions of peers; `tracker.opentrackr.org`, whose operator told TorrentFreak in 2020, "I started the tracker in 2015 when I became frustrated by how many torrents no longer contained any working trackers"; `explodie.org`, whose page says, in full, "I operate a public bittorrent tracker. Please feel free to use it."; `open.stealth.si`; and `tracker.torrent.eu.org`, which spreads its one job, "to coordinate peers," across several servers kept in sync. For browser peers, `tracker.openwebtorrent.com` and `tracker.webtorrent.dev` are the two largest WebSocket trackers by their published figures. One person or a small group runs most of these, and many name no one.

A tracker's address is a hostname, and a hostname can outlive its tracker. `tracker.leechers-paradise.org`, one of the best-known open trackers of the 2010s, now resolves to `tracker.dler.org`, so every old torrent that names it announces to whoever runs that one. The operator of `tracker.ducks.party` does this on purpose, and says so: "I recover expired tracker domains, and these domains will expire again over time, so new torrents should use the stable announce address." Whoever holds a name receives its announces.

## The checkers

Two projects check trackers by asking them for peers the way a client would, and between them they supply nearly every list downstream.

[ngosang/trackerslist](https://github.com/ngosang/trackerslist) is the oldest and most widely read. ngosang has worked on qBittorrent for years, and qBittorrent v3.3.0, in 2015, credits ngosang with the feature that carries lists like this one to users: "Automatically add trackers to new downloads." A tracker gets in by an issue, which ngosang tests and answers; it leaves on its own, since "Tracker is removed after several days of inactivity." The checking program asks every tracker for peers on a few reference torrents, among them a popular one, a very old one, and a fake one, measures uptime and latency and fake seeds, and ranks what's left. The top twenty are `trackers_best.txt`, and `trackers_all.txt` holds every tracker that passes. A separate file of WebSocket trackers, `trackers_all_ws.txt`, has held a handful since 2017. The program's code is private, by choice, because "Publishing the source code will lead to more abandoned forks and more outdated lists," with a stated promise to publish it if the list can't be kept anymore. And the project holds a clear position on addresses: "a public tracker is an infrastructure service and it must be configured with dual IP stack."

[newTrackon](https://newtrackon.com/) checks trackers continuously and publishes their uptime. It continues Trackon, which Uriel built on Google App Engine in 2009, and which went quiet after 2011. CorralPeltzer rewrote it in 2016 and has kept it running since, because most open trackers answer over UDP, and "the original Trackon used Google App Engine which can only process HTTP communications." Each check is a real announce with a fresh random info hash, sent at the tracker's own interval. Uptime is the share of the last thousand checks that got a valid answer, and the stable list, at `/api/stable`, is every tracker at 95 percent or better. Since 2026 a tracker that answers a made-up hash with more than ten peers fails, since no real swarm exists for it. newTrackon keeps one row per hostname, so a tracker serving UDP and HTTPS at one name is checked on one protocol, and each check goes to one of the hostname's addresses, so a tracker that answers over IPv4 and fails over IPv6 can still show 100 percent.

Two newer projects test more. [newTrackon NZ](https://newtrackon.co.nz/), a fork started in 2026, checks IPv4 and IPv6 separately and from several regions, though no list draws from it. The [Torrust](https://github.com/torrust/torrust-tracker) project's tracker checker is a command-line tool for checking a list by hand.

## The lists built on them

Downstream of the two checkers sit the aggregators, lists that merge other lists. [XIU2/TrackersListCollection](https://github.com/XIU2/TrackersListCollection), the largest, merges ngosang's lists, newTrackon's, and a few more, and is written first for users in mainland China, where it recommends IPv6. [adysec/tracker](https://github.com/adysec/tracker) merges dozens of sources every few hours, and others merge those in turn, with lighter checks or none: a DNS lookup, a TCP connection, or nothing at all. One merged list stopped updating in 2024 and is still read by several others. So the original checking happens in two places, ngosang's program and newTrackon, and each list further down reads some combination of them.

## The clients that read the lists

The lists reach users through the clients that fetch them. qBittorrent has added trackers to new downloads since 2015, from a list typed into its settings, and since v5.1.0, in 2025, it can fetch that list from a URL every day; it sets no URL by default. Transmission added a `default-trackers` setting in 4.0.0, typed in by the user. BiglyBT can fetch a tracker template from a URL, and aria2 takes extra trackers on its command line, which popular configurations fill from XIU2's list.

Libraries are the other route, and they work differently: instead of fetching a list, they ship one fixed at a release. libtorrent ships no trackers at all. [create-torrent](https://github.com/webtorrent/create-torrent), the WebTorrent library that builds new torrents, writes eight trackers into any torrent made without its own, and three of the eight are now gone or answer as another tracker. [Trystero](https://github.com/dmotz/trystero), a library that introduces peers in web apps through WebTorrent trackers, ships five. A list a client fetches each day inherits its checker's judgment; a list built into a library is only as current as the library's last release.

## How trackers come and go

The largest open trackers of 2010, PublicBitTorrent and OpenBitTorrent, are gone. In 2012 they went offline for three weeks to protest the traffic of clients still sending HTTP announces to trackers that had moved to UDP, and came back once µTorrent began trying a tracker's UDP address first; today neither hostname resolves. create-torrent's default list keeps a dated record of the turnover, since each change is a commit: in 2015, a commit titled "remove dead trackers from the defaults list" took out two and put in two more, and both of those have since stopped answering as themselves.

The lists measure it too. Of the 49 trackers on ngosang's first list in 2016, three are listed today, and of the 83 on it at the start of 2026, 32 are still there ten months later. Studies from the late 2000s found the same churn: one, at INFOCOM 2007, estimated a tracker's lifetime at "about 390 days," and another, in 2011, found fewer than two percent of the trackers named by discovery sites answering on the morning it checked.

## What no one checked

The checking described above left three gaps.

- **No one checked a WebSocket tracker with a real announce.** newTrackon accepts only UDP and HTTP trackers, and a request for WebSocket support stayed open from 2017 to 2024 with no code merged. The aggregators that test WebSocket trackers open a TCP connection to the port, which shows only that something listens there. ngosang's program completes the WebSocket handshake, and whether it announces isn't published.
- **Few checks tested each address family.** newTrackon's check goes to one address, and ngosang publishes no IPv6-only list, by design. Only newTrackon NZ tests each family separately.
- **The most widely read checker is private.** The method behind the list most clients read is known only from its author's descriptions of it.

## What ftorrent built

ftorrent tracks the trackers in two places, built separately for two different questions. list.ftorrent.com asks how each tracker has done over time, from a server, every hour, and keeps the answer. The Trackers tab in the desktop client asks which trackers answer this machine right now, when the user asks, and keeps only what answered. Each reads the other's output as one source among several, never as the only one, so either keeps working without the other.

### list.ftorrent.com

[list.ftorrent.com](https://list.ftorrent.com) checks every tracker on ngosang's lists, on newTrackon's full list, and on a list of its own, every hour, over IPv4 and IPv6 separately, and publishes the result two ways: [`trackers.txt`](https://list.ftorrent.com/trackers.txt), the trackers that work, in the same one-to-a-line format with a blank line between, for a client's "add trackers from a URL" setting; and [`trackers.json`](https://list.ftorrent.com/trackers.json), every tracker's record, open to any page or tool that wants to read it. The page in front of them shows the list to copy, the last hour's outcomes, filters for building a list of your own, and each tracker's history at its own address, a calendar of six months for each family.

The design follows from the gaps.

- **Every tracker gets a real announce, WebSocket ones included.** A tracker gets a torrent of its own, a random info hash that names nothing, and [libtorrent](https://www.libtorrent.org/) announces to it, so a tracker is judged by the same code the clients built on libtorrent run, with the same handling of redirects, certificates, and protocol quirks. One announce decides the hour. We considered two announcers looking for each other, and set it aside: it would fail trackers that keep one peer per address, spread their swarms across servers, or enforce their announce interval, and it would catch nothing common that one announce misses.
- **Each family is checked from its own network.** One container announces from a network with only IPv4, and another from one with only IPv6, so libtorrent has no choice of family to make, and a tracker that answers over one and fails over the other shows both.
- **Every hour is kept.** A tracker's record reads as a calendar, and `trackers.txt` lists a tracker whose up hours, as a share of the hours checked, reach 95 percent over the last 30 days in at least one family. The bar is newTrackon's, held over a month, so one bad hour never drops a steady tracker, and a tracker with a perfect month that stops answering leaves the list after a day and a half.
- **A tracker that hands out invented peers is left out.** The honest reply to a random hash lists no one, or the announcer alone, and a tracker whose replies list others is sending its users' clients to addresses no swarm put there. Such a tracker stays out of `trackers.txt`, whatever its uptime, until a month passes without it.
- **Once named, a tracker stays checked.** The lists carry the trackers that work today, so a tracker that stops answering can drop off one and return later. list.ftorrent.com keeps checking every tracker any list has named, so the hours it was gone read as down, and its own list keeps every public WebSocket tracker found in use since 2017, gone or not, so one that comes back is noticed. In 2026 November, five of its 41 WebSocket addresses answered.
- **All of it is open.** The program, its database's shape, and the guide to running it are in [the repository](https://github.com/zootella/ftorrent/tree/master/list), so anyone can read how a tracker is judged, or run a second record from somewhere else.

### The Trackers tab

The Trackers tab answers a narrower question, for one person, at one moment: which trackers answer this computer, from where it is on the internet, right now, before it writes them into a new torrent. It holds two boxes, the lists to fetch and trackers of the user's own to check beside them, both saved in ftorrent's settings and filled at first with list.ftorrent.com's `trackers.txt`, ngosang's two lists, newTrackon's stable list, ftorrent's own trackers, and the WebSocket trackers browser peers depend on.

Pressing Check starts by finding which families the machine can reach, and the tab says so, checking and showing only those. It fetches the lists, looks up every tracker's name at once, and announces to each with libtorrent, up to twenty at a time, each judged on its first try. The results arrive as a list ordered by reply time, in milliseconds, fastest first, so the list worth using builds in seconds and can be copied before the slowest trackers finish. Buttons pick from it, everything that answered or the fastest five, ten, or twenty, or twenty at random, and the trackers that answered are saved, fastest first, so the next torrent can start from them without another check, after a restart too. A check in which no tracker answers at all says more about the network than the trackers, so it saves nothing and the last list stays.

One more choice follows from the blank lines. ftorrent announces to every tier, as qBittorrent and Transmission do, rather than libtorrent's own default of the first tier that answers, so a torrent's twenty trackers all hear from it, browser peers on a WebSocket tracker included. The setting is in the settings file, for anyone who wants BEP 12's original behavior back.

## One tracker through the lists

`open.ftorrent.com` serves all three protocols at one hostname: `udp://open.ftorrent.com:443/announce`, `https://open.ftorrent.com/announce`, and `wss://open.ftorrent.com`. Here is where each one appeared on 2026 November 8, and why.

- **ngosang** listed the UDP address 43rd of 71 in `trackers_all.txt`, and the HTTPS address 51st, as `https://open.ftorrent.com:443/announce`. Neither was in `trackers_best.txt`. The WebSocket address was fourth of four in `trackers_all_ws.txt`, as `wss://open.ftorrent.com:443`.
- **newTrackon** listed the UDP address only, since it keeps one protocol per hostname, in its stable list at 99.20 percent. newTrackon NZ listed it among the trackers that pass all its tests over both families.
- **XIU2** carried the UDP address in its best list, which it reached through newTrackon's stable list, and the HTTPS address in its full list. It had no WebSocket address, because its parser keeps only addresses ending in `/announce`, and the one in ngosang's file doesn't.
- **Trystero** listed `wss://open.ftorrent.com` first among its default trackers from its 0.25.3 release, in 2026 July, which it reached through a pull request from ftorrent, not through any list.
- **list.ftorrent.com** lists all three in `trackers.txt`, and records its own UDP tracker's hours from the announces it serves rather than an announce of its own.

So the UDP address reached every list and the HTTPS address most of them, while the WebSocket address reached one list, and its place in a library's defaults came from asking that library directly. That's the gap the rest of this work set out to close: a WebSocket tracker now gets the same real announce, every hour, as any other.
