# Anticipate permission requests

The operating system asks the person a question the first time ftorrent does certain things: listens for connections, sends to the local network, reaches into a folder. Each question comes as a system box that ftorrent never sees, and while it stands, whatever ftorrent was doing fails on the clock rather than on the network. This note is the plan for handling that systemically: which things ftorrent does can raise a box, doing each at a moment the person expects and is likely to say yes, and checking again after some sign they're done with the box, so a wrong answer never stands because someone was slow to click. Started 2026-10-24, at the end of the good roadmap's Good5, from watching one box.

## The box we watched

The Connection tab's Check searches the local network for the router by UPnP, a multicast to 239.255.255.250 on port 1900. The router answers from its own address, so to the macOS firewall the answer is an unsolicited incoming packet, and with the firewall on and ftorrent not on its allow list, the firewall holds the packet and puts up its box: "Do you want the application 'ftorrent' to accept incoming network connections?", with Deny and Allow, and a line that clicking Deny may limit the application's behavior. The person reads it, maybe takes a screenshot, and clicks. Meanwhile the search has its four seconds, hears nothing, and the run ends with "no answer in 4 seconds" on the search's line and the three UPnP reads failing for want of a gateway. The panel's row on what the router speaks names the firewall as the likely cause when ftorrent isn't on its list, which is right, but the facts on the table are still wrong until someone presses Check again. The second run found the router in 44 milliseconds. We saw this twice on 2026-10-24, on a development build and on an installed copy, the second after resetting both gates so the box would come fresh.

The other gate on a Mac, Local Network privacy, did not ask, and the reason turned out to be that it had already been answered. The installed copy carries the sentence macOS would show, "ftorrent wants to access the local network.", in its Info.plist, and the Local Network pane in System Settings listed ftorrent with its switch on before the run, from an earlier run nobody remembers a box for, and still after it. tccutil can't clear that grant: its reset of everything for the bundle reports success and leaves the entry standing, and it has no service name for Local Network, so the pane's switch is the only control, and a fresh box can't be staged from the command line. The grant stood, the search went through once the firewall allowed it, and the pane shows one entry for ftorrent.app, which covers the engine inside the bundle too, since this gate is per bundle where the firewall's list is per program. Apple's technote says the system asks the first time an app sends to a device on the local network or to a multicast address, and that the privilege follows the code signature, which Apple tracks reliably only for an Apple-issued identity; ftorrent is signed ad hoc, and the entry on the pane says the grant held across a rebuild.

On Windows the same shape showed up a week earlier with a different box. The Connection tab's first Check binds a UDP socket on every address for STUN, and Windows Defender Firewall puts up its alert, "Windows Defender Firewall has blocked some features of this app", with the two network kinds as checkboxes. It writes block rules for the current network's kind before anyone answers, and Allow access turns them into allows. The run that raised the box completes with its results unchanged, since the reads that run are outbound and a reply comes back to the socket that sent, but what the firewall will do to a connection in changes with the click, and the panel's firewall rows read what stood when the run began. The note on that dialog is `windows-block.md`.

The engine raises its own. When a session starts it listens on every address, and the macOS firewall asks about ftorrent-engine, the engine rather than ftorrent, some seconds to over a minute after Start rather than at the first listen; Windows asks about a second after. On both, strangers reached the engine over uTP before the box was answered, since a stateful firewall admits answers to what the engine sent first.

## Every box ftorrent can raise

The things ftorrent does that the operating system may stop to ask about, as far as we've seen or can tell from the platforms' documentation. Each is a place to apply the cadence below.

- **Listening, on a Mac.** The application firewall, when it's on, asks the first time a program accepts an unsolicited incoming packet: ftorrent on the UPnP search's reply, the engine on its first connection in after Start. The answer follows the program's path and its signature, so a development build, an installed copy, and the engine inside each are separate questions, and a rebuild that changes the engine asks again. Off by default, so most Macs never see it.
- **Listening, on Windows.** Defender Firewall asks the first time a program binds a socket that could take connections: ftorrent at Check's STUN bind, the engine at Start. On by default, so every Windows copy sees both, once per program path.
- **The local network, on a Mac.** Local Network privacy asks the first time an app sends to a local address or a multicast address, except the network's DNS server, which on most home networks is the router itself. The UPnP search is the first such send; NAT-PMP and PCP to the gateway are exempt where the gateway is the resolver and may ask where it isn't; the engine's local service discovery, off today, would ask when it's on; a peer on the same network reached through the DHT may ask too. Whether an ad-hoc signed app is asked at all is the open question above.
- **Folders, on a Mac.** macOS asks the first time an app reads or writes inside Desktop, Documents, or Downloads, and ftorrent's factory download folder is inside Downloads, so the engine's first write there will ask about ftorrent-engine, and the panel's torrent-file open box may ask about ftorrent. Not yet seen, since nothing downloads yet.
- **Settings pages the app can only point at.** Starting at login, the firewall's allow list, and the local network switch have no box of their own: the app registers or asks, and the person confirms or changes it in System Settings or Windows Settings. The settings page already links to the two login pages; the firewall and local network pages join them in Good9.

What never asks, and shouldn't: Location, which a BitTorrent client has no reason to want, even though macOS and recent Windows keep the Wi-Fi network's name behind it.

## The cadence

Do the thing when the person expects it. Every box above follows an action of the person's: Check, Start, Open…, a download beginning. None of them should follow launch, since a box at launch asks about something the person hasn't done yet, and a person says no to what they don't understand. The Connection tab opens empty for this reason already. Where ftorrent's own words come before the box, as the settings page's sentence comes before the login item, the system's box reads as the second half of something the person started, and the yes is likely.

Then check again, since the person can't click instantly and the first attempt has already failed on the clock. The sign to watch for is the box going away, which ftorrent can't see directly, but its window getting focus back is close: a system box takes focus, and answering it gives focus back to the app, which Tauri reports as a window focus event. On that signal, re-run whatever failed on the clock during the box, as a run of its own in the box's record, so both runs stay, the one that raised the box and the one after it. Where the focus signal doesn't come, or the box was answered from elsewhere, a timer does the same: a check again after ten seconds, and once more after twenty, and then no more, since a box still standing after that is a person who has walked away, and a check that keeps asking the network every ten seconds is the thing the plan was built not to do. The re-run is only for checks that ended in no answer; a check that answered or failed with a reason stands.

The same cadence serves the facts the system can change behind ftorrent's back with no box at all: a firewall switched on, a grant withdrawn, a login item removed in Settings. Good9g in the good roadmap already plans to re-ask those when the window comes forward, and the focus event is that moment too. One mechanism, then: on focus back, and on the two timers after any check that may have raised a box, re-read what the system may have changed.

## What's open

Whether Tauri's focus event fires reliably on a Mac when a system box is dismissed, which decides whether the timers are the fallback or the only signal. Whether the engine's firewall box on a Mac can be brought forward from its minute of delay, or whether its delay is the firewall's own and the panel should just say the box may come late. And where, in the panel's code, the re-run lives: beside connectionRun in `desktop/src/connection.js`, as a second entry point that takes the checks that ended in no answer and runs them alone.
