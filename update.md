# Update

The desktop client checks ftorrent.com for a newer version, and on the user's click it installs it. The check is built and sound: an installed Mac or Windows copy reads the sidecar beside the file it updates from, on a button press and on its own a day or two apart. The install on the Mac is rebuilt on the sequence Sparkle, the updater most Mac apps outside the App Store use, settled on over twenty years, after our first version worked once and showed why that sequence exists. This note is the what and the why. The essay at the top of `desktop/src/update.js` is the full sequence with every path, and `desktop/src-tauri/src/install.rs` is the installer's half; Rust holds no update logic past that moment, only general commands the page sequences.

## The priorities

Reliability first, simplicity second, and the moment the user sees third. A user who waits a second or two with no window and then sees ftorrent back, updated, is fine. A user who meets a broken app or a strange system dialog is done with ftorrent. Where a smoother moment would cost a step that could fail strangely, the plain step wins.

## What's built

- **At startup, can this copy replace itself?** The button offers an update only when the answer is yes: the installed copy in `/Applications`, in a bundle and a folder this user can write, with the data folder on the same volume as the bundle. A copy that fails one of those tests logs why and never offers the button; when a check finds a newer version there, the status line says to get it at ftorrent.com, with the address a link that opens the browser. So a standard user without an administrator's rights and a home folder on another drive end at the download page, by design, rather than in a failed install.
- **The click.** The store reads the sidecar again. The page removes anything a past update left in `update` in the data folder, checks for 1 GiB free, makes the folder, streams the download in under a size ceiling, checks its SHA-256 against the sidecar's, unzips it with ditto, and confirms the bundle unpacked. Nothing has touched the installed app, and a failure anywhere here removes the folder and leaves everything as it was.
- **The handoff.** The page starts the executable inside the newer bundle with `--replace /Applications/ftorrent.app`, and `--log` and the log folder when logging is on, and quits through the ordinary exit: the settings are written, the engine stops, and the lock goes with the process.
- **The installer.** The newer copy sees `--replace` in setup and never takes a lock, starts an engine, or builds a window. It waits for the lock, which the kernel releases only when the old process has ended, takes it, exchanges the two bundles in one step with `renamex_np` and `RENAME_SWAP`, touches the new bundle so Launch Services and Finder read it again, opens `/Applications/ftorrent.app` by its path with `open -n` and `--update`, and exits.
- **The new copy.** Started with `--update`, it waits for the lock rather than handing over, takes it as the installer leaves, opens its window where the old one was, and removes `update`, which now holds the older bundle.

## Why it's shaped this way

Each rule below is one Sparkle follows, and each answers something our first version broke or would have.

- **The old copy quits before its bundle is touched.** Once a running app's bundle moves, macOS's privacy daemon can no longer find its code, and reads and writes in Downloads, Documents, and Desktop fail with "Operation not permitted" for the rest of the process's life, including the resume data libtorrent saves as the engine stops. Sparkle sends an ordinary quit and waits on a kernel exit watch with no timeout; our lock is that watch, keyed on the data folder and already built. The wait has a ceiling of ten minutes, far past any quit, only so an installer never lingers invisibly behind a hung app.
- **One atomic exchange under the same name, then a touch.** `RENAME_SWAP` exchanges the two bundles or does nothing, so a failure leaves the installed app exactly where it was, and Finder sees a single replacement. The first version renamed the running bundle away under a hidden name, renamed the new one in, and deleted the old one beneath Finder, and for an hour afterward dragging a release onto Applications failed with "an item with the name "" already exists." The touch sets the modification time, which Apple's Launch Services guide names as what makes the system register an app again, where Sparkle's source says `LSRegisterURL` "hasn't worked out well in practice."
- **The relaunch goes through Launch Services, by path.** macOS charges privacy prompts and grants to the process responsible for an app: a spawned child answers to its parent, and an app opened by path answers for itself, so a copy the installer spawned directly would answer to a process that no longer exists. By path rather than by identifier, so the system opens this bundle and not another copy that shares its identifier, like a build in the repository's target folder.
- **Something always comes back.** The installer opens whatever is at the target path after the swap, the newer version or the old one, and the log says which. No click leaves the user with nothing running, short of the old copy itself hanging.
- **The newer copy is the installer.** Sparkle ships a small tool of its own and submits it to launchd so it outlives the app. ftorrent bundles nothing and keeps one program: the newer copy runs the installer's steps in the moment before it would take the lock, which is where `lib.rs` already puts what the page can't do because no page exists yet. The page decides everything it can and says it on the command line, and the installer reads only facts about itself.
- **Refuse up front rather than fall back.** Sparkle stages on the destination's volume when the volumes differ and falls back to three moves when the swap fails. ftorrent has one flow: the download and the unzip always happen in the data folder, where the swap is a rename on the one volume every Mac boots from, and the two cases where that isn't so, a standard user and a home folder on another drive, are turned away before the download rather than handled after it. Fewer paths, each of them exercised.

The build box is messier than any user's Mac, with versions made, installed, and trashed all day and dozens of stale Launch Services records from mounted disk images, so a quirk seen only here is weighed against Sparkle's practice rather than built around.

## Windows

The setup program is the orchestrator there: it asks the running copy to exit through its pipe, waits for its files to come free, writes over the install folder, and starts the new copy. `mac2win.md` asks the Windows session to research how the established Windows updaters thread the same needle, then to finish and test that half.

## The public record

Names and Numbers still calls the update check planned, says the client checks HTTPS against the system's trust roots, and doesn't list the request's headers, `User-Agent: ureq/3.4.2`, `Accept: */*`, and `Accept-Encoding: gzip`, the update's download, or that the file's name, `.app.zip.json` or `.exe.json`, tells the server the platform. The planning doc's Automatic Update section still describes Tauri's updater, per-platform manifests, and counting installs from access logs, and its Security section says nothing the page can call starts a process, where `process.rs` now runs and starts programs for the page, as general commands. All of these get corrected once the Mac install has passed its test.

## Tested

The rebuilt install ran on 2026-10-07, from 0.1.1 installed to 0.1.2 published, with the log on. The old copy's quit took under half a second, the installer's work, from taking the lock to opening the new copy, took 44 ms, and the new page was up 0.85 s after the old copy began quitting; the new copy never waited for the lock. No dialog and no Dock icon appeared, the Downloads folder stayed held in the new copy with no prompt, the temporary folder was removed at the new copy's startup, and dragging a release from the disk image onto Applications afterward got Finder's ordinary replace dialog. A slow quit, from a test build that sleeps fifteen seconds on its way out, had the installer wait 14.7 s for the lock and then do the same work; during the wait the installer's own icon stood in the Dock beside the old copy's, since it's a Tauri app with the default Dock presence, which in a normal update lasts fifty milliseconds and is never seen. A refused swap, made by setting the immutable flag on the installed bundle after the old copy had started, had the installer log "Operation not permitted" and open the old copy anyway, which removed the leftover folder at its startup and logged that it can't replace itself. With the flag set before launch, the button stayed Check for Update and the status line read Get the new version at ftorrent.com, with the link opening the browser.
