The user carries this file between the two machines through git: they commit and push it on the Mac, you pull it, you add your answers at the end, and they commit and push it back.

## Rules for this session

- This repository is public, and everything committed to it stays public. In anything you write into a tracked file, refer to the person at the keyboard as "the user", never by name. A path that contains the user's account name gets `username` in its place.
- Git is read-only for you: read status, logs, and diffs freely, but never commit, push, branch, or delete. The user does all of that.

- Never regenerate a lockfile. `pnpm-lock.yaml`, `Cargo.lock`, and `desktop/engine/uv.lock` are pinned on purpose. This round's commit already removed two lines from `Cargo.lock`, `fastrand` and `toml` under ftorrent's own dependencies; if a build wants to change anything more, stop and say so.
- Indent with tabs in any file you edit.

## Background

The last letter, a targeted check of the association gate, was never run, and this one replaces it: its checks are folded in below. Since then the Mac reshaped the desktop client's Rust around one rule, which now opens `desktop/src-tauri/src/lib.rs` as an essay: Rust stays general. It offers commands any desktop application could use, and the page holds all of ftorrent's own logic. `simpler-rust.md` at the repository root has the plan and every decision. What changed:

- **The engine road.** `engine_send` passes the page's JSON commands down to the engine unread, and `engine_take` hands the page the engine's lines from a drained queue. `engine_folders` and the `ready` and `folders` status fields are gone. `engine.py` has a dispatch table. `engine.rs`'s essay has the design.
- **Arrivals.** What reaches a running copy, its own command line or a second launch's handoff, now waits in the same kind of drained queue, taken with `instance_take`, and the page keeps the list. The pipe handoff itself is unchanged.
- **Window placement.** `settings.rs` is gone, and so are the `toml` and `fastrand` crates. Rust builds the window hidden, at any size; `window.js` places it where the settings remember or somewhere fresh, maximizes it if it was, shows it, and then calls `window_revealed`. Until then `bring_forward` does nothing, so a handoff during a cold start can't show the window before it's placed.
- **Associations.** `associate.rs` is gone. `registry.rs` offers `registry_get`, `registry_set`, and `registry_notify`, knowing no key names, and `desktop/src/associate.js` holds the whole policy, porting the Rust version's writes one for one and in the same order. `paths` now reports the executable and the installer's folder, `%LOCALAPPDATA%\ftorrent`, which the page compares with the program's location, ignoring case, as the one gate. Only a copy in that folder registers, silently skipping everything else, a debug or release build from the repository included.
- **Download-folder locks.** `folders.rs` became `locks.rs`: `lock_take` and `lock_release` lock any file. The page makes each download folder's `.ftorrent`, hides it with the new `disk_hide`, and locks `.ftorrent/ftorrent.lock` inside it. Startup locks only folders that already exist; a **Prepare download folder** button on the main page stands in for starting a torrent, making the default folder if it isn't there and locking it.
- **The product's name, written once.** `productName` in `tauri.conf.json` is now the only place the code spells ftorrent. Rust derives the window title, the tray's text, the settings file's name, the lock file, the engine's folder, and the pipe's prefix from it; the page imports the same file through `desktop/src/brand.js` for `.ftorrent`, the ProgIDs and link scheme, and its own text; and the engine gets it in `init` for its client name. Every derived value spells the same as before, so nothing on disk or in the registry should move.
- **Smaller.** Linux now quits when the window's close button is pressed. The settings file's header asks the user to quit ftorrent before editing it. A first run's missing settings file reads `settings: first run, so writing … with every setting at its factory value`. And 37 files lost the path comment on their first line; six files in `open/` keep theirs, because those name where the file goes on a server.

On the Mac everything that runs there passed. Windows is the first place five things can be checked: the Windows-only code compiles, the registry ends up exactly as the Rust version left it, the pipe handoff still arrives through the new queue, maximizing a hidden window doesn't flash, and `.ftorrent` is hidden.

## What to do

3. **Registration, key for key.** Before installing, export what the registry holds now, into a scratch folder outside the repository, so there's something to compare against: `reg export` each of `HKCU\Software\Classes\ftorrent.torrent`, `ftorrent.ftorrent`, `ftorrent.url.magnet`, `ftorrent.url.ftorrent`, and `magnet` under `HKCU\Software\Classes`; `HKCU\Software\Classes\.torrent\OpenWithProgids` and `.ftorrent\OpenWithProgids`; `HKCU\Software\Classes\Applications\ftorrent.exe`; `HKCU\Software\ftorrent\Capabilities`; and `HKCU\Software\RegisteredApplications`. Ask the user to install the new setup exe over the current one, launch from the Start menu, and paste the report. We expect `associations: 2 file types and 2 link types registered, 0 values written`, since the Rust version already wrote every value. Export the same keys again and confirm each file is identical to its before. Any other count is the surprise we're looking for.
4. **A fresh registration.** With ftorrent quit, delete what ftorrent writes and nothing else: its four ProgID keys, `Applications\ftorrent.exe`, `Software\ftorrent\Capabilities`, its value under `RegisteredApplications`, and its values under the two `OpenWithProgids` lists. 5. **A copy outside the installer's folder.** Quit the installed copy, which shares its data folder and would otherwise take the handoff. We expect no associations line at all, and `reg query "HKCU\Software\Classes\ftorrent.torrent\shell\open\command"`, before and after, still naming the installed path.
6. **Download folders, and the tray.** With the installed copy running, hover the tray icon and open its menu: the tooltip should read ftorrent and the first item Show ftorrent, now built from the product name. Then, the report's downloads line ends with the folder's state: `not on this machine` if `%USERPROFILE%\Downloads\ftorrent` doesn't exist, which ftorrent never creates at startup. Press **Prepare download folder** and expect `held`. Confirm with `attrib "%USERPROFILE%\Downloads\ftorrent\.ftorrent"` in `cmd` that `.ftorrent` carries the `H` attribute, and that it doesn't show in Explorer with hidden items turned off.
7. **The engine road.** The report's first lines should read as they always have: the engine line with libtorrent's version, and "the engine has its paths" and "the engine has its folders", which now come from lines the page took and parsed itself. In a debug build's developer tools, opened with right-click and Inspect or F12, run `await window.__TAURI_INTERNALS__.invoke('engine_send', {line: '{"command":"nope"}'})` and confirm the report gains `engine said: unknown command, "nope"`; then run it with `{line: 'a\nb'}` and confirm it fails with `a line for the engine can't contain a line break`.
8. **Arrivals through the queue.** Confirm the pipe's name is unchanged by its derivation from the product name: the report's handoff line and `[System.IO.Directory]::GetFiles("\\.\pipe\") | Select-String ftorrent` should both show `\\.\pipe\ftorrent-` followed by the same sixteen hex digits as the earlier letter's, since the lock file's path hasn't changed. Then repeat the earlier handoff checks against the new queue, on the debug build: a cold launch with `"magnet:?xt=urn:btih:one"` lists `1. launch: magnet:?xt=urn:btih:one`; a second launch with another magnet adds a `handoff` line and exits quickly; and ten at once, `1..10 | ForEach-Object { Start-Process .\target\debug\ftorrent.exe -ArgumentList "magnet:?xt=urn:btih:burst$_" }`, all arrive, with one window, one process, and no `dropped` line.
9. **Window placement.** With ftorrent quit, set the four numbers under `[window]` in `%LOCALAPPDATA%\com.ftorrent.ftorrent\ftorrent.toml` to 0 and launch: the window should appear once, five eighths by one half of the screen, somewhere in the middle. Move it, quit with File, Exit, and relaunch: it comes back in the same place. Maximize it, quit, and relaunch, watching closely: it should come back maximized with nothing appearing at the smaller size first. Restore it, and it goes back to its earlier place. The Mac couldn't check this one, because on Windows maximizing a hidden window shows it, so the page maximizes as its last step before showing.
10. **A click during a cold start.** With nothing running, start two launches as close together as PowerShell can: `Start-Process .\target\debug\ftorrent.exe -ArgumentList "magnet:?xt=urn:btih:cold1"; Start-Process .\target\debug\ftorrent.exe -ArgumentList "magnet:?xt=urn:btih:cold2"`. We expect one window listing both, appearing once, in its placed spot: the second launch's handoff mustn't show the window at the builder's size before the page places it. Run it three times.
