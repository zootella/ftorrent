# The Windows burst

A burst of desktop work done on the Windows machine on 2026-09-25, slotted into the portable sprint between the instance-management step and the steps that follow it. Five things that everything after them leans on, each built, installed, and tested on a real Windows 10 machine the same day: the application icon and its pipeline, the document icon a `.torrent` file wears, the window made in code at the size and place the user left it, settings in a TOML file the page owns, and the file types and link schemes ftorrent registers. One more, the websites' favicon, is planned here and built later.

One section per topic. Each says what ftorrent does, how it works, what was measured, and what is left, and nothing about a topic lives anywhere else. `portable-sprint.md` is the sprint this sits inside; `windows.md` is the letter between the two development machines.

## Icon

The application icon is the brand mark: an orange pill, `#FF7900`, holding two white rings joined by a bar. Two nodes, linked. It is drawn on a sixteen unit grid, `viewBox="0 0 16 16"` with `width="1024"`, so a viewer opens it large while every coordinate stays a small number that lands on a pixel at the smallest sizes, and it is two elements, a rounded rectangle and one path with two arcs.

**One drawing, three sources, one generator.** `tauri icon`, Tauri's own tool, takes a square SVG and resizes it edge to edge into every platform's icon files at once: the Windows `.ico`, the macOS `.icns`, the Linux PNGs, the Store logos. It has no notion of a platform safe area, and the platforms disagree about one. Windows and Linux want an icon that fills its canvas; Windows treats a margin as a defect. macOS draws an icon exactly as authored, on a grid where every neighbor leaves a margin, and a bare shape sized against Apple's own round icons lands at 892 of 1024. The Windows 10 Start menu tile wants the mark inset on the tile's background, at 676 of 1024. So the pipeline feeds the generator three sources, `src-tauri/icons/app-icon.svg`, `app-icon-mac.svg`, and `app-icon-tile.svg`, which are the same two elements seen through three viewBoxes: `0 0 16 16` full bleed, `-1.184 -1.184 18.368 18.368` for the Dock, `-4.118 -4.118 24.237 24.237` for the tile. A wider viewBox shows more empty space around the same drawing, so the generator's edge-to-edge render comes out inset, and nothing is redrawn.

**Routing.** `pnpm icons` runs the generator three times: the full-bleed source into `src-tauri/icons/` itself, the Mac source into a gitignored scratch folder `.mac/`, the tile source into `.tile/`. Then `scripts.js icons-collect` copies the few wanted files out from under the generator's names, `mac/icon.icns` and the two tile PNGs, so no run can overwrite another's. `tauri.conf.json` picks: `bundle.icon` names `icons/icon.ico`, the three Linux PNGs, and `icons/mac/icon.icns` rather than the full-bleed `.icns` beside it, and Tauri chooses the `.icns` for the Mac by extension, so that one entry is the whole per-platform switch. The installer and uninstaller wear the same `.ico` through `bundle.windows.nsis.installerIcon` and `uninstallerIcon`; without them the setup exe shows NSIS's stock icon. The tray picks the icon up from the window's default icon. The engine, `ftorrent-engine.exe`, keeps PyInstaller's stock icon by choice; it suits the era the client is drawn from, and it is one `icon=` argument in the spec if that ever changes.

**The Start menu tile.** Windows 10 reads `ftorrent.VisualElementsManifest.xml` from the folder holding `ftorrent.exe`, a Windows 8.1 mechanism now in Microsoft's archived documentation, finished and stable. `bundle.resources` lands it and the two tile PNGs beside the executable, because on Windows the resource directory is the executable's own folder, with no installer template involved. The schema: `BackgroundColor`, `ForegroundText`, and `ShowNameOnSquare150x150Logo` are required; the two logo attributes are all or nothing, and naming one without the other makes Windows silently ignore the file; images at most 1024 square and 200 KB; the only diagnostic is Event Viewer event 28032 under `Microsoft-Windows-Shell-Core/Operational`. Windows 11 has no tiles and ignores the file. The manifest ships `BackgroundColor="black"`, and on the Windows 10 machine the tile shows the theme's own color behind the inset mark, milky white in light mode and near black in dark, like Firefox, Chrome, Edge, and Visual Studio Code do, whatever color their manifests declare. Measured that morning: the schema allows `#RRGGBB` or sixteen named colors and no `transparent`, and no light and dark pair; every browser installed declared a dark or brand color under a transparent logo and got the theme color; and a manifest with `#5F6368`, then `#000000`, then the same file under the installer's own shortcut, got the theme color every time. So the value is never painted on this machine, `black` is the honest one to write, and most Windows users are on 11, where no tile exists at all. A tile that stays dark on a light Start, which one other application here shows, was left unexplained; a guess, untested, is that Windows judges the logo's own color against the theme tile and paints a contrast only when it must.

**Lessons worth keeping.** Generated icons are committed artifacts frozen at the CLI that made them: before CLI 2.9.3 the generator left a grey fringe on every curved edge, and upgrading fixed nothing until someone re-ran it, so run `pnpm icons` after a CLI upgrade as well as after an artwork change. The generator writes `.icns` entries in an unstable order, so `icon.icns` shows as modified after every run even when the pixels are identical. And it writes `android/` and `ios/` trees nothing here uses; they are committed as generated, since the icon has settled and they will rarely change.

**Measured.** Full bleed on the ordinary icons; the tile's mark at 65.5 percent of its canvas; `icon.ico` with six layers from 16 to 256; edge pixels within rounding of the orange. Seen on a real install: the setup exe, the taskbar, the tray, and the Start menu tile. Left: a look at the mark in a real Dock, from the Mac.

## Torrent icon

A `.torrent` file in Explorer wears a document icon, not the application icon. An application icon is meant to be unmistakable in a taskbar, which is exactly the wrong property on a file: a folder of torrents would be a folder of identical pills. So `src-tauri/icons/torrent.ico` is the donut on the sheet: a blank page with a folded corner, carrying one orange circle with a white dot at its center. One node, waiting to join the others; the brand is two nodes linked. `bundle.resources` lands it beside the executable, and the file type registration names it as the `.torrent` type's `DefaultIcon`, with the executable's own icon as the fallback if the file is missing.

**Only Windows needs one.** macOS composes a document icon itself, a page with the application's icon set on it, for any type an app declares. Linux draws the desktop theme's own icon for the file's MIME type. Both look right with nothing supplied, so nothing is.

**Drawn, not generated, on the sixteen grid.** A document icon sits among other documents and wants whole pixels at the small sizes, where one grid unit of the brand mark is less than a pixel and the rings turn to an orange haze; that was tried first, at two sizes, and it read well at 256 and not at 16, 20, or 24. The donut instead has its center and both radii on whole units of the same grid, an orange circle of diameter 8 at (8,9) and a white dot of diameter 2, so at 16 pixels every edge sits on a pixel with nothing to hint by hand, and the larger sizes are the same drawing scaled, sharp where the scale is whole and gently soft where it isn't, which is what the sheet's own border does at those sizes too.

**The icon studio.** `desktop/icon-studio/` is where all three icons are made: Windows only, PowerShell, by hand, never read by the build, the way Tauri never looks in `desktop/linux/`. Three drawings in, `brand.svg`, `donut.svg`, and `sheet.ico`, the blank page with its eight layers from 256 down to 16 including the 20 and 40 that Windows wants at 125 percent scaling; three icons out, `favicon.svg`, `ftorrent.ico`, and `torrent.ico`; one command, `Update-Icons.ps1`, which draws the donut onto every sheet size, packs the layers into the `.ico` with every layer a PNG and the largest first, copies it into the build's icons folder, writes the favicon and the three application sources from the brand by viewBox, runs `pnpm icons`, and copies the generated `.ico` back as the record of what shipped. `Split-Ico.ps1` takes an `.ico` apart into its layers, converting a layer stored as a bare Windows bitmap into a PNG; `Test-Ico.ps1` asks the Windows shell for every layer the way Explorer does, because .NET's own icon class refuses PNG layers it did not write while the shell reads them all. The studio's README has the whole flow, and the scripts each open with an essay on the format they touch.

**Measured.** The sheet copied bit for bit and untouched outside the donut at every size; the shell extracts all eight layers; both `.ico` copies byte-identical between the studio and the build; the studio reproduces its outputs byte for byte on a second run. Seen in Explorer at every view size, and beside the executable on a real install.

## Favicon

Planned, not built. The websites' icon is scattered today: open.ftorrent.com uses an earth emoji, which is right for a page whose subject is the planet's peers and stays; ftorrent.com, a Nuxt site, and docs.ftorrent.com, a VitePress site, set none. Both get `favicon.svg` from the studio, the brand as it is, copied by hand into each site's public folder and linked inline from each site's head configuration as `<link rel="icon" type="image/svg+xml" href="/favicon.svg">`. An SVG favicon scales to every tab and pinned-site size and is what current Chrome, Firefox, and Edge read; Safari still wants a raster, so `ftorrent.ico` goes beside it as `favicon.ico`. Site work, for a later session.

## Window

The window is made in code, from Tauri's `Ready` event, rather than declared in `tauri.conf.json`, and the move did three jobs at once.

**It fixed the cold-start race.** A window declared in the config is built, with its web view inside, before setup runs, and setup is where a second launch finds the lock held and leaves. On Windows two launches a few tens of milliseconds apart both built a WebView2 on the same profile, and the one that left took the shared browser process down with it, leaving the winner with a lock, a pipe, an engine, a tray icon, and no window it could ever show; `windows.md` step 9 found it and this is its fix. Made from `Ready`, a leaving launch never has a window at all. Measured after the change: three rounds of two launches 17 to 27 milliseconds apart against the installed executable, each leaving one process, one engine, six WebView2 helpers, one visible window listing both requests, and empty stderr on both losers, where every round before had left a window-less winner and a `Failed to unregister class Chrome_WidgetWin_0` line.

**It is sprint step 3.** `WebviewWindowBuilder::data_directory` is where a portable copy points WebView2's profile into `portable/`, and that call exists only on the builder. The window is built with the data folder startup resolved, portable or installed. The check that a portable run leaves the host's `EBWebView` untouched waits for a portable copy to exist.

**It lets the window open where the user left it.** ftorrent is single window, so it dictates both size and position every time the window is created and never lets the operating system place it. After a session the settings file holds six numbers, all in CSS pixels, so scaling never enters the file, and whether the window was maximized:

```
[window]
x         = 340      the window's outer position
y         = 210
width     = 1200     and its inner size
height    = 600
maximized = false    true opens it maximized, and the four numbers above are where restoring it goes

[screen]
width  = 1920     the resolution of the monitor the window was on when this was recorded
height = 1200
```

On startup, `monitor_from_point` names the monitor under the middle of the saved window, not its top left corner: Windows counts an invisible resize border, 7 pixels at 100 percent, as part of the window, so a window snapped to the left half records `x = -7`, a point just off the screen. If there is such a monitor and its resolution equals `[screen]`, the ground beneath the user's preference is the same, and the rectangle is replayed exactly, so a window parked in a corner against the taskbar comes back there tomorrow, avoiding the chrome while blind to it. Otherwise recalculate: no monitor under the point because an external display was unplugged, or a different size because the user changed the resolution, rotated the monitor, changed the scaling, or plugged into a television. That is the whole guard. It fingerprints the ground rather than reasoning about it, never enumerates the other monitors, and a single-monitor user and a multi-monitor user run the same two lines.

**Recalculating, which is also the first run.** The window is sized to five eighths of the primary screen's width and half its height, and dropped at a uniformly random spot inside a field centered on the screen that is three quarters of it each way. The margin the field leaves on every side, an eighth of the screen, is deeper than any taskbar, menu bar, or dock, so the window misses the operating system's chrome by construction without ever asking where the chrome is; on a 1920 by 1200 display that is a 1200 by 600 window somewhere in a 1440 by 900 box. The one screen query is the primary monitor's size and scale, needed to state the fractions in CSS pixels, and it carries no judgment. The randomness also keeps an installed copy and a portable copy from stacking exactly when both are on a first run. The four fractions are constants at the top of `window.rs`, under its essay, with a comment each.

**Recording.** The page listens for the window's move and resize events and records outer position, inner size, and the current monitor's resolution into the settings store, in CSS pixels via the scale factor, skipping while minimized, where Windows reports a position like (-32000, -32000), and while fullscreen. While maximized it records only the flag and leaves the numbers where the window was before, so the file always holds a normal size and place; `window.rs` builds the window there with `.maximized(true)`, and the restore button goes back there. When that reaches disk is under Settings. No `minWidth` or `minHeight`: CSS degrades rather than breaks. Not needed and not used: the work area query, monitor enumeration, any settle or cascade logic, or `tauri-plugin-window-state`, which keeps its state in a file of its own outside the settings file and so outside the portable promise.

**Measured.** A first launch landed in the middle field; a drag, a resize, and the X wrote real numbers under `[window]` and `[screen]`; a relaunch came back to the same place and size; a move followed by File > Exit came back the same way. After the review that moved the lookup to the window's middle and added the maximized flag, on the installed build: a window snapped to the left half, recorded at `x = -7`, came back snapped, where before it had opened in the middle field; a window exited while maximized came back maximized, and its restore button went back to where it had been before; one exited while minimized came back normal, since nothing is recorded while minimized.

## Settings

`ftorrent.toml` replaces `ftorrent.json`, and the page owns it.

**TOML, for the person who opens it in Notepad.** Every setting is written out, always, under a comment saying what it does, with its factory value at the end of the line, so the file is the documentation of every knob ftorrent has; JSON has no comments, so a JSON settings file can never explain itself. TOML also forgives what JSON punishes: no trailing-comma trap, no whole-file failure over one quote. The file stays in the plain dialect, sections with simple keys, strings, numbers, booleans, and flat arrays. The rename reaches `paths.rs`, the sprint document, and the portable marker, which becomes `portable/ftorrent.toml`; the planning document waits for its correction pass at the sprint's end.

```
[note]       text = ""                              a note to yourself, shown on the main page; it exists to prove a setting survives a restart
[downloads]  folders = ["~/Downloads/ftorrent"]     where torrents go; ~ is home, ./ is the folder ftorrent is in, an absolute path is exactly that place
[window]     x, y, width, height, maximized         outer position and inner size, css pixels, and whether it was maximized
[screen]     width, height                          the resolution of the monitor the window was on, css pixels
```

**The page owns settings and the logic that manages them.** Application logic lives on one side of the boundary, the page's, where the store is; calls down to Rust and to the engine are atomic, dumb, pipe-shaped commands, and nothing is replicated or shared across the boundary. So `settings.js` has the schema, the factory values, the comments, the repair, and the render, `stores/settings.js` does the reading and writing around it, and Rust knows the file only as a path to hand over, text to write when asked, and a few numbers to read early. Both sides parse TOML: `smol-toml` on the page, the `toml` crate in Rust. Rust's early read, `settings.rs`, takes the six window numbers and the maximized flag and nothing else, because the window is built before the page exists; it reads and never writes, repairs nothing, and answers "nothing recorded" on any trouble, leaving a malformed file for the page to report properly a moment later.

**Reading rules.** A value the schema can use replaces the factory value; a value of the wrong type or outside its check is reported and the factory value stays; a key the schema doesn't know is reported as a typo rather than ignored. A file that won't parse leaves everything at factory, is reported, and is left exactly as it is, since it may be one typo from right; the Rust code this replaced drew the same line. So is a file that couldn't be read at all, a lock or a permission, since the settings in it are the user's. A file that parses is repaired and rewritten. A backslash inside double quotes starts a TOML escape, so a Windows path typed by hand as `"C:\Users\me"` doesn't parse, and `"D:\new"` parses to a newline, which the folders check turns away; the file's comment asks for forward slashes, and single quotes, `'D:\torrents'`, also keep every backslash as typed. A missing file is created whole on the first run.

**Download folders moved to the page.** Rust used to read them from the file and start the engine with them before the page existed. Now the page reads the settings, expands the paths against anchors Rust provides, the home folder and the program's folder, and calls a Rust command with the absolute list; Rust passes it to the engine in a `folders` message, which the engine echoes back, and the page shows "the engine has its folders" when the echo matches. The engine's `init` carries only the data folder and the state file now. The sprint's next step, locking each download folder, inherits this interface: the lock stays in Rust because it is OS level, and which folders to ask about is the page's.

**When settings save.** Two kinds, two timings, no debounce anywhere. Every ordinary setting writes immediately on the user's action: the page renders the whole file and calls Rust's write command, one action, one write. Window geometry is recorded in the store on every move and resize and written when the window is closed with its X, which in ftorrent hides it rather than quitting; a drag of a hundred segments is a hundred in-memory updates and no writes. A backstop covers the user who never presses X and quits from the tray or the File menu: on each in-memory change the page also hands the rendered text down to Rust, an in-memory copy, and Rust writes it from the `Exit` event, the one every quit path reaches, where a synchronous write is fine and a round trip to the page is impossible. A crash between loses the position, and the user drags it once more. Writes are plain; a settings file this small is not where a torrent client breaks.

**Measured.** A clean install created the file with every setting under its comment; a note typed and saved showed in the file and came back after hiding the window, showing it from the tray, and File > Exit; the engine echoed the resolved folders. The lockfile gained nine lines, all `smol-toml`; `Cargo.lock` gained one for `toml`, already in the tree. A file broken by hand, `folders = ["C:\Users\me"]`, was reported on the page with the parser's own pointer to the character, ftorrent ran on factory settings with a fresh window place, and the file's bytes and timestamp came through a launch, a moved window, and File > Exit unchanged.

## Associations

ftorrent registers two kinds of file, `.torrent` and `.ftorrent`, and two kinds of link, `magnet:` and `ftorrent:`, offering itself as a handler and taking nothing a user or another program holds.

**The polite way, on Windows.** An installer app has no manifest to declare its types in; that mechanism exists only for packaged apps from the Store. Its only channel is the registry, and the modern versus old distinction is about what gets written there. The old way: the installer writes the extension's default value, `.torrent = ftorrent.torrent`, seizing the default at install time. This is what Tauri's `bundle.fileAssociations` does on Windows through its NSIS macro, which is why that key stays out of `tauri.conf.json`. The new way, `associate.rs`: the app itself, at runtime, writes under `HKCU` only, reading each value first so an unchanged launch writes nothing, and notifies the shell only when something moved. Per file type it writes the ProgID, `ftorrent.torrent` named "Torrent File" and `ftorrent.ftorrent` named "ftorrent File", each with its `DefaultIcon` and its `shell\open\command`; itself into the extension's `OpenWithProgids` list, which is the offer; the extension into the executable's `SupportedTypes`; and the pair into `Capabilities\FileAssociations`. Per link scheme it writes its own ProgID, `ftorrent.url.magnet` or `ftorrent.url.ftorrent`, with an empty `URL Protocol` value, an icon, and a command, and the pair into `Capabilities\URLAssociations`, so a choice in Settings names ftorrent's own key. Once, it writes the executable's `FriendlyAppName` and command, the `Capabilities` block's name and description, and last, on purpose, `RegisteredApplications`, the line that publishes ftorrent to Settings > Default apps, written only after everything it points at exists. Never written: an extension's default value, or `UserChoice`, which Windows seals with a per-user hash so only the user, through the system's own interface, can set a default. Microsoft's own current API for unpackaged apps writes the same polite set.

**Links: assertive, and taking nothing.** Windows keeps a scheme's default in its own sealed `UserChoice`, and when no user has chosen, it falls back to the class key named for the scheme, `magnet` itself. That class is shared: any program can write it, and many clients register nothing else. ftorrent writes it only while it runs no command or already runs ftorrent's, reading through `HKEY_CLASSES_ROOT` so that a client installed for the whole machine counts as holding it. On a machine with no torrent client, a clicked magnet reaches ftorrent with no user step; where another program holds the class, ftorrent leaves it alone and waits to be chosen. A choice of ftorrent names `ftorrent.url.magnet`, so it holds however often another client rewrites the shared class, and a choice of a client that registered only the shared class names `magnet`, which ftorrent then never touches.

**Where it runs.** From setup, after the lock is won, installed release builds on Windows only. A portable copy registers nothing, because a stick ejected would leave a dead association pointing at a path that no longer exists. A debug build registers nothing, because its executable lives in `target/debug`, a moving target. The page shows one line: how many types registered, how many values written, and any scheme whose shared class was left to the program that has it.

**What arrives.** Nothing new was needed on Windows: the operating system opens a file or a link by running `ftorrent.exe` with it as an argument, and the instance handoff already forwards a second launch's arguments to the running copy and lists them on the page. On macOS the types and schemes go in `Info.plist`, and `RunEvent::Opened` delivers both files and URLs from Launch Services; that is the Mac side's to build.

**Measured, on the Windows machine.** The first launch wrote 26 of 27 values, the one already present being another client's `URL Protocol` marker on the `magnet` class, which is now shared; the second launch wrote 0. Explorer showed "Torrent File" and kept the previous default handler's icon and double-click, since that client holds the user's choice. On two real Ubuntu 24.04.3 torrent files: Open with listed ftorrent; chosen with ftorrent not running, the file arrived as the new process's own launch argument; chosen with ftorrent running, it arrived as a handoff into the same window; chosen with the window hidden in the tray, it brought the window back. An `ftorrent:` link clicked in Chrome arrived as a handoff with the window hidden, with it showing, and as a cold launch, with only Chrome's own first-time prompt in the way. Settings > Apps > Default apps listed ftorrent with `.torrent`, `.ftorrent`, `MAGNET`, and `FTORRENT`; the user gave it all four there, which is the one place a default is meant to change. After that the two files wore the donut in Explorer, a double-click started ftorrent cold with the file as its argument and a second double-click handed off into the same window, and both Ubuntu magnets clicked in Chrome arrived whole, tracker and all. These runs were of the first version, which wrote the shared `magnet` class on every launch and named it in `URLAssociations`; a review then replaced both with the ProgIDs and the guard above. Installed after that, the registry held `ftorrent.url.magnet` and `ftorrent.url.ftorrent` with the installed command, `URLAssociations` named them, and the shared `magnet` class, already running ftorrent's command, stayed ftorrent's, with no scheme left to another program. The user's standing choice still named `magnet` from before the change; choosing ftorrent again in Settings is what moves it onto `ftorrent.url.magnet`, and that check is still to do.

**Left.** A bare NSIS uninstall leaves every registry key behind, pointing at an executable that is gone. The fix would be `bundle.windows.nsis.installerHooks` naming an `.nsh` with `NSIS_HOOK_PREUNINSTALL` that deletes only ftorrent's own keys; deferred, since NSIS is a convenience ridden on its defaults and the leftovers are inert, with one exception: a shared scheme class ftorrent claimed while it was empty goes on pointing at the missing executable, on a machine where no other client had one. A "Default torrent app" panel, where a Windows button opens `ms-settings:defaultapps?registeredAppUser=ftorrent`, whose parameter may work only on Windows 11 with plain `ms-settings:defaultapps` as the fallback, is the planning document's and comes with the interface.
